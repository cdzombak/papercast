# “papercast” application spec
## Project Overview
`papercast` is a Go application that creates, on disk, an RSS feed from your unread Instapaper articles. It’s run via cron. When it runs, it syncs its database with Instapaper, uses Google’s Chirp 3 HD to create MP3s of any new articles, and removes articles that have been archived or deleted from Instapaper. The MP3s and an RSS feed file are written to disk for some other process to serve.

## Functional Requirements
### Instapaper Authentication Flow
Authentication uses Instapaper's xAuth flow (`oauth/access_token` with `x_auth_mode=client_auth`), which exchanges a username/password for a permanent OAuth 1.0a token pair. Credentials are supplied once via a `-instapaper-login` CLI flag (interactive prompt for username/password); the resulting token and token secret are persisted at a path specified in the config for Instapaper credentials. The consumer key/secret for the registered Instapaper API application are supplied via the `instapaper` config section, not prompted for.

The end-user facing process is documented in the README.

The implementing agent should research and choose an appropriate OAuth library rather than writing the OAuth process from scratch.

The Instapaper credential file is JSON format and created with 0600 permissions.

#### Suggested Workflow
The end user is intended to run the application initially with `-instapaper-login -config` , to go through the Instapaper authentication process and generate the Instapaper auth file. Subsequent runs are then via cron, with no interactive component.

### Instapaper Sync
The program syncs the “unread” Instapaper folder to its SQLite database.

Use the `have` parameter on `bookmarks/list` for incremental sync: pass the IDs you've already processed and Instapaper tells you what's new/changed.

Store relevant state for efficient sync in the sqlite database, along with the articles’ metadata.

The program never archives or delete bookmarks on Instapaper — this program only reads from Instapaper.

Deletions — used to remove items from the feed and their corresponding MP3s from disk — come only from the response's `delete_ids` field, never from their absence in the bookmarks list (that’s the point of the `have` parameter: bookmarks we already have will be missing from the next sync by definition).

Set `limit=500` on the `bookmarks/list` endpoint and never fetch more than one page, due to (reported) Instapaper API limitations.

#### Instapaper State Stored
In addition to articles’ URLs, titles, and other metadata, the application tracks:
- the article HTML as retrieved from Instapaper
- if/when the article was successfully converted to a podcast episode, its MP3 filename, and its GUID in the RSS feed
- whether the article was rejected for being too short

This allows the application to tell whether an article was successfully processed, and retry articles that were successfully synced but not successfully turned into episodes.

Articles rejected for being too short are never retried.

### Article HTML
Retrieve article HTML from Instapaper’s `bookmarks/get_text` API; do not scrape webpages for content.

Skip any article that’s less than 200 words. (The user can set this number in the config.)

### Article Descriptions
Article descriptions are generated by asking an LLM, via an OpenAI-compatible API, to summarize each article. The article content as fetched from Instapaper is provided to the LLM in this request.

Note that this step is skipped for articles rejected as too-short.

Text provided to the LLM is the extracted block text from the Text Structure step. Max input size is configurable via `llm.max_input_chars` (default to a reasonable length for GPT 5.6 Luna); truncation, if necessary, happens at a block boundary.

The OpenAI-compatible API endpoint, API key, and model to be used are configured in the `llm` section of the program’s configuration.

Article descriptions are generated after the article content is fetched from Instapaper, and stored in the database, before the application moves on to the TTS phase. A failure to generate a description causes a descriptive warning to be logged, but does not fail the article’s processing.

If article description generation fails, the fallback description (not saved to the DB) simply reads like:
```
"Article Title" from article-domain.com
```

On subsequent runs of the program, for any articles that had LLM description generation fail previously, LLM description is attempted again. If it succeeds, the result is stored in the DB and the RSS feed is updated to include the description.

LLM Prompt:
```
Summarize the following article in 1 paragraph. Do not include any introductory text, just the summary:

<article>
[ARTICLE TEXT HERE]
</article>
```

LLM requests timeout (and article description falls back to the default) after 60 seconds (configurable via `llm.timeout`).

The `llm` config section is optional and LLM descriptions are disabled by default. They are enabled by setting `llm.enabled: true`.

### Text-to-speech
Text-to-speech is performed using Google’s Chirp 3 HD ( https://docs.cloud.google.com/text-to-speech/docs/chirp3-hd ) voices.

The user must provide a list of usable voice names in the `tts` config section. A random voice is selected for each article. The choice is stored in the database for each article, ensuring that in case of a [partial] TTS failure the same voice is used when retrying.

Before each article, add a short introduction including the title and source domain for the article. The user can disable this in the config if desired; it’s on by default.

TTS generation is sequential, not concurrent, to avoid rate limits imposed by the TTS API. After a server side or rate limit error from the TTS API, exponential backoff is used to retry the request, until it is eventually allowed to fail, which fails the whole article’s processing for the run.

#### Text Structure
Article HTML from `bookmarks/get_text` is parsed into an ordered list of structured blocks (paragraph, heading, list item, blockquote), not flattened into a single string. Paragraph boundaries must survive extraction; everything downstream depends on them.

The minimum-word count (for determining whether to reject an article as too-short) is computed over the concatenated text of the extracted blocks, after HTML parsing and before any SSML rendering.

#### SSML
SSML use is optional, controlled by `tts.ssml` (default: false). Chirp 3 HD supports a subset of SSML tags for synchronous requests; refer to https://docs.cloud.google.com/text-to-speech/docs/chirp3-hd#chirp3-hd-ssml .

When disabled, blocks are joined with blank lines and sent as plain text.

When enabled:
- Each chunk is a self-contained, well-formed `<speak>` document.
- Paragraphs are wrapped in `<p>`
- A `<break>` separates the article intro from the body.
- Text is XML-escaped (`&`, `<`, `>`). Note that article titles routinely contain ampersands; unescaped input returns HTTP 400.

#### Chunking
The per-request limit for synchronous Chirp 3 HD synthesis is 5000 bytes, measured over the serialized request payload — so in SSML mode, tags and escaping count toward the budget. The chunker measures rendered output, not source text length. The effective limit is configurable via `tts.max_chunk_bytes` (default: 4500, leaving headroom).

Chunks are packed on paragraph boundaries: whole blocks are appended until the next one will not fit. A single block that exceeds the limit on its own is split into sentences using https://github.com/neurosnap/sentences ; a single sentence that still exceeds the limit is split on whitespace as a last resort. Sentence segmentation is a fallback path, not the primary one.

Chunks are requested in MP3 format. Resulting chunks are stitched into the output file using ffmpeg. The program creates a temporary directory underneath the destination directory, where chunks are staged before assembly.

Care is taken at every opportunity to generate natural-sounding speech around chunk boundaries.

##### Chunk Caching
Chunk identifiers are derived deterministically from the full synthesis request that produced them — the rendered chunk payload (including SSML markup, if any), the voice name, and any other synthesis parameters — not from the source text alone. This ensures that toggling `tts.ssml`, changing chunk size, or a different voice selection cannot silently reuse stale chunks.

When retrying generation for a failed article, cached chunks are used if present.

Chunks are generated/downloaded to a temporary filename and only when completed successfully are they moved to their “permanent” name in the temporary directory. This ensures that cached chunks are always valid for re-use, never truncated or corrupt.

The temporary chunk files are removed after they have successfully been combined into an output file, and the output file has successfully been published in the output directory.

#### Google Cloud Auth
Authentication to Google Cloud uses a service account key file via Application Default Credentials. The `tts` config section specifies `google_service_account_key_path`; at startup the app sets `GOOGLE_APPLICATION_CREDENTIALS` to that path (if not already set in the environment) before constructing the Text-to-Speech client.

The end-user facing process is documented in the README. Note in the instructions that the service account should be scoped to the Cloud Text-to-Speech API only.

### Retry/Error Policy
**Instapaper sync:** fail the whole run.
**Content fetch, GCP TTS generation, or other error while generating a single article episode:** fails the affected article; the application moves on to the next article.

Take care that sufficient state is preserved in the database to resume from any failed operation. For example:
- given an unprocessed article left from a previous sync, but which does have article content in the database, the program does not refetch article content. It proceeds to the TTS step, reusing any cached chunks found on disk.
- given an unprocessed article with no article content in the database, article content is fetched and written to the DB before proceeding with the article processing pipeline

The number of attempts at processing each article is tracked in the database. 3 total attempts are made to process each article successfully. After 3 attempts, we can assume something’s wrong with the article and fail it. Any cached chunks for the article are removed from the temporary directory after the final failure.

The time of the last attempt at processing each article is also stored in the database. At least 60 minutes (time is configurable by the user) must pass between retries of the same article, regardless of how frequently the program is run. An article skipped because it was last attempted too recently does not count as an error, for the purpose of determining an exit code.

### Output Audio
Output MP3 files:
- include ID3 tags for title and author.
- are encoded at a reasonable bitrate for spoken word
- are mono, 44.1 kHz
- have names deterministically generated based on the article ID

### Output RSS Feed
The output RSS feed is a well-formed RSS feed that obeys best practices for podcasts. It includes:
- enclosure `length` (size in bytes) for each episode
- `itunes:duration` for each episode
- cover art (user-specified URL from the config)
- metadata (title, language, `itunes:author`) as configured by the user in the config
- `<link>` for each episode (the article’s link)
- `<description>` for each episode (LLM-generated, CDATA-wrapped)

Use each bookmark's saved date, not generation time, for pubDate.

GUIDs are generated deterministically from each article’s Instapaper ID.

Note that this is not intended to be a public podcast, so full iTunes compatibility is not a concern.

### Output Directory Cleanup
When an article is archived or removed from the “unread” collection on Instapaper, its MP3 file is removed from the output directory.

### Configuration
Configuration is via a YAML file, passed via the `-config` flag, defaulting to `./config.yaml`.

The configuration YAML file is separated into logical sections such as `tts` (text-to-speech API setup & settings), `feed` (metadata to be embedded in the feed, base URL under which the feed & MP3s are available), `output` (directory in which to write the feed & MP3s), etc.

Config is validated at startup. The language code in the voice name must match the configured language; validate at startup rather than failing per-article.

`config.example.yaml` is provided in the repo, showing users how to configure the program.

### Debug mode
The application has “debug mode,” which allows the operator to process a single article and examine how it was chunked and what the outputs were. This is activated by passing `-debug article-id`, referring to the article’s Instapaper ID.

In this mode, Instapaper sync is not run. The program skips directly to run the article-processing pipeline for the given article. (If the article isn’t in the DB at all, it fails. If it’s in the DB but has no stored HTML, it fetches the article content, stores it in the database, then proceeds.) Any previously cached chunks for the article are removed.

While processing, it generates an HTML file containing, in clearly delineated blocks with word wrap enabled, the exact text or SSML sent to the TTS API for each chunk. This is followed by an `<audio>` element offering to play the chunk in question. The HTML file lives in the temporary directory alongside the audio chunks.

Debug mode also runs an LLM description generation for the article, regardless of whether it’s been run before. This result is included in the HTML debug file, but not written to the database.

Interim chunks are _not_ removed after a debug-mode run; they’re left in place for debugging.

Debug mode:
- writes the final MP3 file to the temporary directory and includes it, with an `<audio>` tag, at the top of the debug HTML output. it does not move the final MP3 to the output directory or publish it in the RSS feed.
- does not consume the article’s 3-retry budget or update the article’s last-attempt-at value

### CLI
The CLI allows specifying these flags:
- `-config`: path to config YAML, discussed above
- `-debug id`: runs debug mode for a given article ID
- `-list-articles`: performs the Instapaper sync but does not process any articles; just lists the article’s Instapaper ID, source, and title, and exits `0`.
- `-instapaper-login`
- `-log-level`: optional, defaults to `info`
- `-version`
- `-help`

### Other
“Article domain” and “source domain” for an article refer to the article’s URL’s host, stripped of `www.`.

We can assume we’re working with English for now. If it’s cheap and easy to make the language configurable, do so; otherwise, skip it.

Exit codes:
- 0: success
- 1: fatal error or failure that affects all articles (e.g. Instapaper sync failure, or all articles failed processing)
- 8: partial success (e.g. some articles failed processing but others succeeded)

## Out of scope
- This application does not serve the resulting MP3s or RSS feed over HTTP; that’s left to an external webserver.
- Overlap protection — ensuring only one copy of this process is running — is left to the operator. The README provides an example of how to accomplish this using the `flock` binary on Linux.

## Implementation Details
- Language: Go
- Database: SQLite
- Database library: modernc.org/sqlite
- TTS library: cloud.google.com/go/texttospeech/apiv1
- RSS generation library: [eduncan911/podcast](https://github.com/eduncan911/podcast)
- ID3 tag writing library: https://github.com/n10v/id3v2

Data model is left to the implementing agent, except where data-model requirements are specified elsewhere in this document.

Care is taken to avoid the bad defaults listed in https://mort.coffee/home/sqlite-editions/ , and to follow best practices outlined in https://kerkour.com/sqlite-for-servers .

### Logging
This application uses the Golang standard library’s structured logger.

### Build Process & Artifacts
A Makefile is provided that can run:
- lint (golangci-lint, plus any other linters that might be helpful for this application)
- actionlint (for GitHub Actions YAML)
- test (runs the test suite)
- build (build for the current platform/architecture to `./out`)
- build-docker (builds a Docker image for the current machine)
- clean (cleans `./out`)

GitHub Actions CI workflows are provided that:
- On push or PRs, runs lint, actionlint, and the test suite
- On tags like `vX.Y.Z`, requires lint and the test suite to pass, then builds Docker images for arm64 and amd64 and pushes them to Docker Hub
- Creates a GitHub release
- Updates rolling `vX` and `vX.Y` release tags

The version number is embedded in the binary and the Docker image.

The implementing agent should refer to https://github.com/cdzombak/ebird-rss for an example
Makefile and GitHub Actions setup that I prefer.

### Dockerfile
- The Dockerfile specifies no UID/GID; running as a specific user is the operator’s responsibility.
- Users are expected to provide mounts for: the Google credentials file, Instapaper credentials file, config file (typically readonly), DB directory, and output directory. (Note that the user may choose to provide a single directory that contains the config and credentials files, if they prefer.)

The Dockerfile is based on some minimal or slim Docker image whose package repositories include the necessary deps, including ffmpeg.

A two-stage Dockerfile is used (one for build; one for deployment).

### Tests
Tests never touch the network or a real Instapaper/Google Cloud account. The relevant Instapaper and LLM APIs are stubbed with `httptest.Server` returning canned fixtures; interaction with the Google Cloud API is not tested directly. Rather, the TTS client is wrapped in an interface that can be substituted for testing. The database is a temporary SQLite file per test. Anything time-dependent takes an injected clock, and fixtures use fixed timestamps.

### Architecture
The application is split into modules with clear lines between them, allowing e.g. Instapaper to be switched out for Pocket, or Google Chirp to be swapped out for an OpenAI TTS model, without changing unrelated parts of the program. For example, the core “driver,” Instapaper client & synchronizer, LLM description generator, text-to-speech engine, and RSS renderer should all be separate modules.

### Write Atomicity
The podcast feed file and public-facing MP3 files are written atomically (write to temp directory, then rename to destination).
